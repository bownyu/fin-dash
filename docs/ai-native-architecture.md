# FinDash 架构设计：本地业务内核、AI 能力与交互

设计版本：1.0 · 2026-10-03。状态：**审阅后的目标设计，供后续 agent 实施**。

本文件取代此前 A–E 轻量改造草案，不是实施完成记录。审阅对象是 fin_dash 的 codex/ai-native-lightweight 工作区，包含已有未提交改动；wallet_apk 是旧版 React / Capacitor 项目。本次仅交付设计文档，不递增应用版本、不发布 APK。接口、节点、查询语言与新提示词，除明确列为现有能力外，均待实现。

## 1. 结论与阅读入口

保留 **Flutter + Dart 业务逻辑 + 原生 SQLite + 少量 Kotlin 平台适配** 的模块化单体。当前本地账本、整数分金额、提交后发布状态、AI 提案与人工确认的方向合理。需要重构的是责任边界、数据访问成本和执行协议。

优先级如下；相关接口在首次实施前一起确定：

1. 不配置 AI、断网或模型超时，手动记账、账户、统计、导入、通知核对和备份仍正常使用。
2. 页面、语音、通知、导入与 AI 使用同一份业务规则。
3. AI 能发现应用能力，获得带口径与来源的数据，编写有界查询程序，准备可审阅的变更。
4. 用户补充、修改、取消、确认、撤销都是任务事件；语言准确、简短、与真实状态一致。
5. 图形界面渲染上述事件和状态，视觉优化遵循同一套业务协议。

AI native 指业务能力、上下文、任务与交互从接口层即可被 AI 使用。**它不要求基础功能经过模型，也不要求大模型在手机本地运行。** 本地语音识别与云端语义理解是独立能力。

## 2. 从用户价值推导约束

用户需要“账准确、操作省事、理解自己的钱”。每项抽象都必须服务于这三个结果。

| 事实 | 架构推导 |
| --- | --- |
| 金额与账户关联不能靠概率保证 | 余额、退款、查重、账户有效性由确定性领域代码判断 |
| 点保存需要可靠结果 | 一次事务保存账本、来源状态与回执；落盘后才显示成功 |
| AI 服务会慢或失败 | 网络不进入账本写队列；基础页面不等待 AI 就绪 |
| 页面与进程会消失 | 持久化草稿、任务、用户问题、方案和回执；不靠内存 Future 续接 |
| 用户不应重复描述上下文 | 页面选择、期间、附件和任务用结构化引用传递 |
| 自然语言可能含糊 | 只问阻塞正确执行的问题；保留已知字段，可准备部分先准备 |
| 模型不能永久记住全部细节 | 核心机制常驻提示，能力按需发现，用版本与行为评测检验理解 |
| 数据量和聊天会增长 | 查询、上下文、缓存和执行资源有上限；成本随影响范围增长 |

减少重复规则、无关数据复制、重复确认和无用模型调用。不能为了减少代码行数取消事务、来源证据、恢复副本或冲突检查。

## 4. 总体架构

~~~mermaid
flowchart TD
  UI[Flutter 页面与表单] --> VM[页面状态与交互控制器]
  OS[Android 小部件与通知] --> AD[平台和来源适配器]
  IMPORT[导入与语音草稿] --> AD
  VM --> APP[应用能力 Queries / Commands]
  AD --> APP
  CHAT[聊天与页面 AI 入口] --> RT[TaskRuntime 与 ContextAssembler]
  RT --> MODEL[模型协议适配器]
  RT --> REG[能力目录与查询程序解释器]
  REG --> APP
  RT --> IX[InteractionRequest 与 ReviewPlan]
  IX --> VM
  VM -->|已核验用户事件| APP
  APP --> DOMAIN[纯 Dart 领域规则]
  APP --> REPO[Repository 与 UnitOfWork]
  REPO --> DB[(SQLite 与恢复副本)]
  REPO --> EVENTS[回执与按域变更通知]
  EVENTS --> VM
  EVENTS --> RT
~~~

方框表示责任，不要求每个方框成为 package、服务或独立运行进程。

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| domain | 交易、账户、预算、退款规则；金额、ID、日期类型 | Flutter、HTTP、SQLite、工具名称 |
| application | 查询命令、来源用例、预览、授权核验、事务组织 | Widget 布局、模型生成 |
| data | 唯一账本存储、查询、迁移、恢复、提交队列 | 模型决策和确认弹窗 |
| agent | 任务、上下文、模型调用、能力发现、查询编程、提示词 | 直接改账或取得数据库连接、密钥 |
| presentation | ViewModel、原生卡片、编辑、导航、可访问性 | 余额公式、查重授权、落盘成功判定 |
| platform | Kotlin 麦克风、通知、小部件、系统文件桥 | 第二套账本或交易校验 |

采用构造注入和按域 Listenable 即可，不要求更换状态管理库、引入微服务或通用工作流引擎。本项目的多入口重复规则足以支持一个纯 Dart 领域层；无需为简单显示逻辑套多层抽象。[Flutter 架构建议](https://docs.flutter.dev/app-architecture/recommendations)

三条执行路径：

- 手动记账：表单 → SaveTransaction → 提交时重验 → 本地事务 → 回执，模型调用为 0。
- AI 分析：任务上下文 → 查询能力或查询程序 → 有口径的数据 → 简短回答，无写入确认卡。
- AI 修改：准备方案 → 按需补字段 → 一张方案卡 → 用户确认选中范围 → 本地重验与原子提交 → 确定性回执。成功反馈不等待模型再次生成。

## 5. 业务内核

### 5.1 必须统一的规则

1. 内部金额为整数分，工具字段为 amountCents / balanceCents 并携带 currency。当前仅支持人民币，显示层格式化成两位小数。
2. 新交易必须有正金额、有效类型、用途、日期、有效未归档账户及合法分类；转账要求两个不同账户。
3. 编辑交易撤去旧影响再应用新影响，不能叠加两次；已提交记录对外不可变。
4. 余额 = 期初余额 + 已入账交易影响。校正当前余额调整期初余额，不虚构收入。
5. 总资产与负债按 includeInTotal 范围计算。归档保留历史且禁止新记账；是否纳入总资产由独立字段决定。
6. 转账不计入收支；在全部相关账户均纳入统计范围时保持净资产不变。跨统计范围转账可能改变该范围的净资产。
7. 提交队列内检查最新锁定状态；解锁和恢复走显式维护命令，不能把恢复入口一起锁死。
8. operationId 为稳定业务幂等键；同 ID 不同参数报冲突。模型 toolCallId 不是可靠业务幂等键。
9. 一次操作在一个事务内提交相关账本、来源状态、任务状态和回执；失败不发布内存状态。
10. 提交重验相关记录版本、方案版本与选择范围；撤销是检查执行后状态的新事务，不能覆盖后续修改。

### 5.2 保留来源差异

| 入口 | 来源特有规则 |
| --- | --- |
| 页面 | 当前记录版本、必填字段、刚才的保存动作 |
| AI | 来源证据、歧义字段、待确认方案；普通模型只能准备 |
| 语音 | 稳定 entryId、一次一句草稿、补充字段；识别与语义解析分离 |
| 通知 | 持久化事件后 ACK、来源幂等、退款核对原支出及累计退款 |
| 导入 | 文件记录 ID、账户映射、可能重复项核对、保持当前余额选项 |

抽取共享内核时不能删掉这些差异。导入保余额需要同时调整期初余额。当前退款以收入方向记账，原始收支继续使用现有口径；未来“扣除退款后的净消费”必须是独立 metric，不能悄悄改变旧总额。

### 5.3 数据分域与权限

目标逻辑域：ledger、tasks、conversations、preferences、memory、sources，可共存于一个 SQLite 文件。

现有 WalletMetadata 是降低复制成本的过渡结构，不是权限边界。settings.budget 属于业务数据，extras 中的提案和回执涉及授权；不能因为叫 metadata 就允许任意写入。长期收敛为有类型的命令。

WalletStore.data 逐步改为不可变视图。final 元素不代表列表或嵌套 JSON 不可变。旧 change 保留在受控兼容适配器内，页面和 AI 不得直接取得任意 mutation 回调。

## 6. 存储、查询与迁移

### 提交和恢复

应用用例在一个 UnitOfWork 中读取相关版本、核验规则和授权、计算 ChangeSet，并在一次本地事务中落盘。ChangeSet 仅保存操作和受影响记录，不是第二套账本。成功后发按域变更通知。

保留校验和、revision / generation、旧 JSON 源文件、恢复前快照及损坏恢复副本。现有主库与 ATTACH 恢复副本采用的事务机制不能为性能直接切换 WAL；日志模式变化须单独验证跨文件故障原子性。[SQLite 跨文件事务条件](https://www.sqlite.org/lang_attach.html)

### 逐步降低成本

- 先将聊天、记忆、配置与财务载荷隔离；token 只更新当前消息。
- 再由命令显式提交增删改记录，去掉全快照差异扫描；任务和聊天也按记录更新。
- 最后完善数据库分页与汇总、分段启动；启动加载账户、首页汇总和首屏，其他页面按需读取。

QueryRepository 先允许当前内存实现，后续换 SQL 不改变 API 语义。查询包含范围、指标口径、版本、采样时间、完整性和分页信息。全量汇总与当前明细页严格分开。多步查询使用一致逻辑快照；旧快照不能保留时拒绝旧游标、整体重查，不能拼接版本。

### 关联迁移

在记录查询 schema 实施前冻结：categoryId、分类显示名称快照、sourceType/sourceId、originalTransactionId。历史缺失来源允许 unknown，不按金额时间自动认定同一交易。分类按类型与名称映射，歧义保留待处理。

日期模型区分绝对时间、录入时区 / 业务日期、日期精度。旧无时区记录按旧显示语义迁移，不能直接假定 UTC。

一个权威交易存储配可重建索引。旧格式用于兼容读取和备份，不长期双写两份业务记录。数据库版本、备份 schema、应用版本分别管理。迁移回滚、旧备份往返、拒绝未来 schema 降级、损坏恢复是发布门槛。

## 7. Flutter / Android 的运行边界

Flutter 画页面，Dart 业务层处理规则，Kotlin 接系统能力，SQLite 保存事实。后台执行与进程存活不等于持久化。

- Widget build 不做全量查询、文件解析或业务提交；ViewModel 订阅必要结果。
- 财务、任务、聊天、偏好分域通知；AI busy 与调试日志不触发财务页重新查询。
- 保留已有懒列表、键盘局部订阅、延迟建页、token 局部更新。
- async 不自动把 CPU 工作移出 UI isolate。大导入、解码与重聚合放后台；跨 isolate 只传所需数据。Web 不承诺原生 compute 的并行效果。[Flutter isolates](https://docs.flutter.dev/perf/isolates)
- 同进程内保留共享 FlutterEngine 与单一写入口；Kotlin 只传事件、请求 ID 和用户动作。
- Engine 单例不能跨进程死亡保存状态；恢复依赖 task / draft / receipt，不依赖 onDestroy。[Android 生命周期](https://developer.android.com/guide/components/activities/process-lifecycle)
- 普通聊天可中断续接；需要延后持续执行的维护任务才接系统调度，不做后台 AI 轮询。[后台任务](https://developer.android.com/develop/background-work/background-tasks)
- 小部件录音遵守前台服务和麦克风权限；拒绝授权保留文本入口，不声称无限后台录音。[前台服务限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
- 模型请求独立 requestId / 取消令牌。初始可以一个活动模型请求加短队列；语音忙时保留草稿并明确排队 / 停止选项。手动保存从不进入 AI 请求队列。

## 8. AI 能力与节点

每项能力的定义包含稳定 ID、输入输出、effect、范围、验证、查询或 prepare 方法、策略版本、界面标签。JSON 工具 schema 和执行分派出自同一注册表；页面直接调用强类型 API。

模型默认具备已授权范围内的读取和方案准备能力。财务执行、扩大授权、外部导出走独立应用命令。记忆和偏好也有代码策略：当轮偏好无需永久写入；明确要求长期记住时允许相应保存并给可撤销回执；模型推测不自动写成人格画像。

应用知识由三部分组成：代码注册表生成的能力目录、有测试的 AppSpec 语义说明、ContextAssembler 提供的当前环境。app.describe / capabilities.search 用于按需展开，运行记录 appSpecVersion / capabilityVersion / promptVersion。不能靠一句“你完全了解应用”保证理解，必须通过[提示词评测](ai-native/system-prompts.md)。

AI 自编工具采用 QueryRecipe：模型声明参数、选择数据集、过滤、分桶、分组汇总、比较与排序，运行时校验后本地执行。例如“对比近三个月工作日午餐开销”可以组合成此前没有专门预设的参数化工具。

QueryRecipe 是有类型、有预算的领域查询语言，不获得 shell、任意 Dart / Python、文件、网络或 SQL 连接；超出算子能力时明确说明不足。它仍允许 AI 编排新的查询算法，而不局限于固定报表名称。语法和执行边界见[协议](ai-native/node-and-tool-contracts.md)。

节点是输入、上下文、理解、查询、澄清、方案、等待用户、提交和呈现这些流程边界。多数为普通 Dart 函数，只有语义理解和解释需要模型。任务独立于聊天消息；等待用户时释放模型连接和数据库锁。

## 9. 交互与语言

| 场景 | 默认表现 | 用户动作 |
| --- | --- | --- |
| 查询余额 / 汇总 | 直接回答，按需附数据卡 | 无确认 |
| 缺一个账户 | 保留已填字段，提供真实账户选择与自由输入 | 只补缺项 |
| 只读日期不明确 | 采用合理范围并说明，可调整 | 通常不阻断 |
| 写入关键字段含糊 | 一张补充卡聚合相关字段 | 补充后预览 |
| 批量修改 | 一张方案卡，明确项与待核对项分开 | 确认当前选中项 / 调整 / 取消 |
| 手动表单 | 保存动作已表达该表单的提交意图 | 无额外 AI 确认 |
| 保存失败 | 保留草稿、选择，说明未保存 | 原处重试 |
| 保存成功 | 确定性短回执和可用的撤销入口 | 无须确认成功 |

询问缺失信息与批准变更是两类事件。InteractionRequest 可渲染于聊天或原页面，支持文字和可访问性回退。推荐选项不等于已同意；口头“确认”不自行兑换为本地执行授权。

默认语言预算是偏好，不机械截断：

- 简单事实 / 成功：1–2 句，通常 60 字以内。
- 补充：1 句具体问题，必要时加 1 句解释；相关字段可同卡填写。
- 分析：结论先行，最多 3 条观察，通常 120–300 字；用户要求再展开。
- 方案：1–2 句说明关键变化，不复述卡片。
- 错误：明确是否保存、保留什么、下一步做什么，不倾倒异常栈。

不从消费推断人格，不以责备语气谈钱；区分观察、推测和建议。金额有查询依据，成功状态有回执依据。

图形区块限定为 text、metric、table、chart、question、changePreview、receipt。模型提出显示意图，应用验证数据引用并渲染原生组件；不执行任意 HTML / JS。一任务只保留一个当前有效主卡片，历史可折叠。按钮写具体动作；暂定项默认不选；调整沿用任务；旧版本失效保留选择并要求重新审阅。

优先显示范围、金额、账户、日期、影响和不确定项。工具 ID、token、内部节点进入可选详情。320px、大字体、键盘、屏幕阅读器、返回键都需验收，图表有文字替代，长明细懒加载。[Flutter 性能建议](https://docs.flutter.dev/perf/best-practices)

## 10. 成功标准

硬门槛：

- 非 AI 主流程无模型、密钥或网络依赖。
- 聊天保存不扫描财务记录；token / 日志引起的财务页重建为 0。
- 整批一次事务，失败不污染内存或磁盘；旧审阅不可提交。
- 查询耗尽预算明确返回不完整，分页明细不充当全量总额。
- 等待模型、用户或文件期间不持有账本写锁。
- 权限由运行时核验，无成功回执不能称已保存。

真机检查不同账本规模的输入、滚动、启动、保存、查询、UI / raster 帧时间、掉帧率和内存峰值。60Hz 约 16.7ms、120Hz 约 8.3ms 是单帧预算；具体机型与 p95 门槛在建立基线后记录。本次没有真机 profile，不能宣称流畅性已验收。

实施顺序、各阶段门槛和后续 agent 的交付要求见[实施与验收](ai-native/implementation-and-validation.md)。先完成一个可恢复、可回滚的纵向场景，再扩展能力。计划、实现与验证分别记录。
