# 页面性能检查（2026-10-02）

检查范围：键盘高度订阅、输入引起的重建、账单与账户流水、搜索与账本派生数据、聊天流式输出、导入、统计绘制及存储。结论来自代码审查和 Flutter widget/domain 测试；没有真机 profile 帧时间、内存峰值或 GPU 数据，不能等同于整机流畅度验收。

## 已检查、保留现有机制

- 聊天页：消息列表懒加载；流式回复通过局部 ValueListenable 更新；现有性能测试验证历史 Markdown 和输入框不会随 token 重建。
- 微信 Excel 导入：解析已通过 compute 执行，预览使用 SliverList；原生平台无需在 UI isolate 直接解压解析 Excel。Web 的 compute 不具备同等隔离保证。
- 图表：CustomPainter 根据数据变化决定 shouldRepaint；没有发现每帧主动无条件重绘。
- 主导航：首次访问后保留页面，未访问页延迟创建；TickerMode 关闭非活动标签动画。
- 设置与账户编辑：未发现整页直接订阅 viewInsets 的同类问题。筛选弹层的键盘订阅只影响弹层，不影响账单页面。
- 支付确认：记录使用 SliverList；选择时仍会遍历候选记录计算状态，未对大批量记录做真机耗时测量。

## 仍需 profile 验证的风险

1. **大账本保存、启动和恢复**：0.1.0 已进一步切换原生端至 SQLite 增量写入（见文末）。列表复制、可变元数据深拷贝、跨 isolate 消息复制和差异扫描仍随账本增长，但普通写入不再编码或重写整本账本。需要真机测量剩余暂停与内存峰值；不能把“增量写入”理解为所有 CPU 操作均为常数复杂度。
2. **大量历史记录的 Widget 创建**：通知历史、操作历史等仍使用 PageList 的 children 列表。ListView 的元素布局是懒加载的，但 build 时会创建所有 Widget 描述。比已修复的整日 Column 更轻，仍需在大量记录下测量后改成 builder。
3. **统计与导入预览计算**：统计分组、导入查重及选中汇总会遍历数据。已有排序和余额缓存，但没有覆盖所有派生结果；应以实际数据规模决定进一步缓存范围。
4. **绘制与后台页**：浮动控件使用模糊，主页面 IndexedStack 保留已访问页面；可能带来 GPU 合成、内存和非活动页布局成本。没有真机证据，未直接删除视觉效果或更改导航状态保留行为。

建议用 Android profile/release 构建分别测试 1千/1万笔账单：中文键盘开关、搜索连续输入、长列表滚动、保存、切换统计期间，记录 UI/raster p95、掉帧和内存峰值。60Hz 单帧预算约 16.7ms，120Hz 约 8.3ms；这些是测量标准，不是本轮实测结果。

## 后续：保存链路优化

- `WalletData.clone` 复用字段不可变的账单、账户、分类及快捷记录，复制各列表；profile/settings/chats/extras 等可变 JSON 树递归深拷贝。原先整本 JSON 编码、解码和重建领域对象的流程被移除。
- `wallet_codec.dart`：达到 500 条主要记录或估计较大元数据时，使用 compute 执行完整校验与 JSON 编码；较大载荷的启动解码也使用 compute。小账本保留直接编码，避免每次支付录入都承担后台任务启动开销。
- 原生 `storage_native.dart`：路径在主 isolate 解析；文件读取、旧副本校验、新副本 SHA-256、JSON 封装及写入在后台执行。不在后台调用平台插件。
- mutation 回调仍在原来的顺序队列执行；校验和落盘成功后才发布新快照、通知 UI。回调不跨 isolate，通知批量确认等依赖回调结果的语义保留。
- 保持现有文件格式、校验和、备份和恢复行为。Web 的 compute 在当前事件循环执行，不承诺 Web 具有原生平台同等的后台隔离。

桌面 Flutter test / JIT，10,000 笔合成账单、5 次克隆中位数：旧 JSON 克隆 226,961µs，新结构克隆 72µs。该样本主要是不可变账单，不含大量可变聊天元数据。完整校验加编码同步为 29,337µs，后台任务墙钟时间为 32,078µs；等待期间主 isolate 的 1ms 周期计时器执行 20 次。后台任务并未让总工作量消失，其价值是让主 isolate 能继续处理事件；这些数字不是手机帧率或完整保存耗时。

可复现命令：`flutter test tool/benchmarks/wallet_save_benchmark_test.dart`。新增快照测试覆盖可变树隔离、大账本编码校验、写失败后队列恢复以及恢复操作隔离；原生存储测试覆盖较大 Unicode 载荷与损坏后的备份读取。

保存优化后的验证：全量 `flutter test --no-pub` 为 162 项通过、1 项私人样本测试跳过；独立 1 万笔基准通过；`flutter analyze --no-pub` 无问题。Widget 测试的大账本准备阶段通过 tester.runAsync 等待真实 isolate，避免把后台任务放入模拟时钟后错误挂起。

上述中间方案随后被 0.1.0 原生 SQLite 后端取代；Web 和旧 JSON 兼容路径继续使用快照编码。

## 0.1.0：SQLite 增量存储已落地

- 原生入口 `storage.dart` 使用 `storage_sqlite.dart`；浏览器继续使用原存储。旧 `storage_native.dart` 留作 JSON 兼容与对照基准。
- 账单、账户、分类、快捷交易、目标和聊天按条存储。profile/settings 等按键存储，通知等列表按记录存储，变化行才 JSON 编码、计算校验和并写 SQL。
- 不压缩删除后的顺序编号，因此删除中间一笔不会重写后续全部账单。显式重排和中间插入按需更新顺序。
- 普通交易重用上一次已校验的不可变记录，只对新建/修改交易检查字段，同时检查全局 ID 唯一性。账户结构变化、迁移、恢复仍执行完整验证。
- 主库与恢复副本使用 SQLite ATTACH、DELETE rollback journal 和 FULL synchronous，在同一事务内更新两个文件。保留回滚机制，不采用无法保证跨文件原子提交的 WAL 模式。副本是最新已提交数据的冗余拷贝，不是历史版本管理。
- 存储版本与 generation 防止旧实例覆盖新数据。旧 JSON 主文件及备份在完整校验后迁移，迁移失败可以重试，原文件保留；损坏数据库保留后才从已验证副本恢复。JSON 导入导出继续有效。
- 后台仍会扫描差异并复制消息图，启动仍会加载整个工作集，尚未做数据库分页查询。这些剩余成本与“每次重写整本 JSON”已分离。

桌面 JIT 基准（`tool/benchmarks/sqlite_save_benchmark_test.dart`）：10,000 笔已有账单、连续 5 次单笔新增，JSON 后端含落盘的中位时间 249,726µs，SQLite 后端 39,541µs；每次新增修改 1 条业务数据行（外加恢复副本及 revision 元数据）。此数据不能代替 ARM64 真机 profile。

最终验证：175 项测试通过、1 项私人源文件测试跳过；SQLite 专项覆盖迁移回退、迁移中断重试、两个实例首次打开、失效版本拒写、副本写入失败回滚、未提交事务关闭、单库/双库损坏、显式恢复、未来 schema 拒绝降级，以及账单/聊天/通知的顺序与增量行数。Android Release 构建通过，APK 内已核验 `lib/arm64-v8a/libsqlite3.so`。
