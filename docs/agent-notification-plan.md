# FinDash 智能体与 Android 通知识别实施方案

日期：2026-10-01。目标设备：小米 17 Pro，实际 HyperOS / Android 版本待真机记录。

本轮交付可查询真实账本、识别账户截图、提出账户和交易变更的智能体，以及低功耗通知采集、待确认账单和操作历史。用户最新决定是先实现智能体与通知识别，个人微信／支付宝账单文件导入暂缓。保留现有 JSON 备份恢复语义，不增加 CSV、XLSX 或 ZIP 导入。

## 产品范围与验收边界

| 模块 | 本轮实现 | 后续事项 |
|---|---|---|
| 智能体查询 | 稳定账户 ID、完整账户设置、日期与账户筛选、分页、分类汇总、预算与分类查询 | 更丰富的长期趋势图表 |
| 智能体操作 | 新增／更新账户与交易、预算调整；先提案、再用户确认，操作历史与有条件撤销 | 删除账户、批量破坏性操作不开放给模型 |
| 截图 | 相册选择、发送前预览、显式启用图片模型能力、通过工具产生账户／交易提案 | 连续截屏、自动读取其他 App 页面不做 |
| 通知识别 | 微信／支付宝原生通知监听、本地规则、持久收件箱、连接状态、人工核对后入账 | 自动入账需真机验证后另行开启 |
| 特殊交易 | 退款、转账、还款及金额缺失明确标记，用户核对；不凭关键词直接计入收入 | 退款与原交易关联、部分退款净额统计 |
| 个人账单导入 | 仅预留来源扩展和去重元数据 | 整个导入流程暂缓 |

应用继续使用 Flutter；系统集成使用 Kotlin，无需 Root、Xposed、Shizuku、无障碍或常驻截图。网页版保留现有预览功能，通知能力仅 Android 可用。

## 智能体结构

```text
文字／用户选择的截图
  → 模型请求（能力开关、超时、取消、有限工具循环）
  → 工具路由
     ├─ 查询：WalletStore 的真实数据、确定性汇总
     └─ 写入请求：AgentActions 验证并保存提案
          → 人类可读预览 → 用户确认 → 原子保存 → 操作回执
```

模型不接触任意 SQL、文件写入、密钥或原生权限接口。截图、通知和账单备注是数据，不是可执行指令。模型不能调用确认或撤销接口，也不能通过参数把待确认状态改为已执行。用户在 App 内按确认按钮是实际写入的入口。

### 查询工具

- `get_accounts_overview`：返回 ID、类型、余额（分与显示金额）、信用额度、账单日、还款日、统计开关、归档和备注。银行卡识别信息使用账户备注描述，不推断完整卡号。
- `query_tx`：日期起始含、结束不含；账户 ID、分类、类型、搜索词、offset、limit（最多 200）。汇总覆盖全部匹配结果，明细分页；返回交易 ID 和下一页标志。
- `get_app_settings`：返回预算、现有分类及账户类型，不返回 API 密钥、服务凭据或不相关设置。
- `get_pending_actions`：让模型知道提案仍待确认；执行结果以本地状态为准。
- 复用现有财务状态、异常检测、用户明确陈述的记忆工具。

分析缓存必须包含问题、日期范围、账本版本内容与模型配置，避免相同期间的不同问题得到同一份旧回答。携带图片或产生写入提案的请求不使用分析结果缓存。

### 写入提案

工具为 `propose_account_change`、`propose_transaction`、`propose_budget`。所有金额用整数分，不允许 NaN、负交易金额、非法日期、未知账户、相同转出转入账户等数据进入账本。更新账户只覆盖明确给出的字段，保留其余设置。

提案数据包含：ID、类型、目标 ID、变更内容、变更前快照、创建时间、说明、状态、执行时间和执行后快照。状态为 pending → applied / rejected，applied → undone。重复的相同待确认命令复用提案；重复点击确认不重复写账。

确认时重新验证目标状态，拒绝覆盖提案之后发生的修改。写账、状态更新和回执在同一次 `WalletStore.change` 中保存；保存失败不更改内存。撤销前检查执行后状态仍匹配，存在后续编辑时拒绝撤销并说明原因。

账户当前余额和期初余额严格区分：新增账户可提供当前余额；已有账户余额校正必须展示原余额、目标余额及差额，确认时按已有流水重算期初余额，并检查关联流水没有变化。截图时间不明或较旧时，模型应先询问，不将旧快照冒充当前余额。

### 截图与模型能力

用户手动选图并可移除，发送按钮明确表示将图片发送到所配置的服务。使用支持图片输入及工具调用的模型，能力通过每个提供商的图片开关明确配置，不根据模型名字猜测。

单次最多一张 JPEG／PNG，限制大小并缩放；使用多模态消息传输。图片仅在当前请求／失败重试的内存中保留，不写入账本、备份、历史聊天或调试日志。历史只保留“附有截图”的标记；新请求不自动重发旧图。失败提示需区分不支持图片、网络和格式错误。

识别结果必须区分可用额度、总额度、本期应还和总欠款。缺失字段省略，不填零。匹配账户依赖稳定 ID 和用户确认，不能仅凭“微信支付”推断扣款账户。

## Android 通知采集

```text
系统 NotificationListenerService 回调
  → 包名白名单 + 支付语义过滤
  → 本地规则解析（不联网、不启动 Flutter）
  → SQLite 持久化原生收件箱
  → App 前台通过 MethodChannel 分页读取
  → 写入账本 extras 中的候选记录并去重
  → 保存成功才向原生收件箱 ACK
  → 人工补全／核对 → 同一账本事务中生成交易及入账标记
```

### 权限与生命周期

- 默认关闭。页面先解释只处理微信／支付宝支付相关通知，再由用户打开开关并前往系统通知使用权设置。
- 服务使用 `BIND_NOTIFICATION_LISTENER_SERVICE` 声明；这与发送通知的权限不同。
- `onListenerConnected` / `onListenerDisconnected` 更新连接状态；重连请求有限触发，不循环保活。
- 退出页面不影响原生收集。用户强行停止、撤回权限、系统省电策略均可能中断；不承诺全量捕获。
- 页面区分采集开关、授权状态、连接状态、最后接收时间、队列数量及容量异常。回到前台刷新，不用定时器轮询。
- 本轮不申请忽略电池优化、不持有唤醒锁、不建立前台保活服务、不注册周期任务。确有缺失时再根据小米实测选择必要设置。

### 规则和数据质量

白名单为 `com.tencent.mm` 与 `com.eg.android.AlipayGphone`。提取标题、正文、展开正文、文本行、通知 key、发布时间。微信需要支付服务标题等强信号，普通聊天中出现“元”“付款”不能直接成为消费账单。广告、待付款、失败、关闭、验证码等排除；多个不同金额不猜测。

解析输出包含 sourcePackage、notificationKey、eventId、postedAt、title、原始支付文本、amountCents（可空）、kind（expense / income / transfer / refund / repayment / unknown）、merchant、ruleVersion、needsReview 和原因。包名及事件 ID 不允许由模型伪造为已验证来源。

通知时间仅代表收到通知的时间；交易真实时间可人工调整。金额缺失、退款和方向不明仍可进入待处理记录，但不能直接入账。退款第一版保留待处理与忽略入口，提示通过原交易核对，避免把退款自动算作收入。

去重以原始事件指纹识别完全相同回调。不同通知内容但相同金额／相近时间只标记疑似重复，不自动删除。用户确认重复风险后才允许入账；通知更新不能覆盖已经入账的交易。

### 存储与隐私

原生队列与 `findash_ledger.json` 独立，使用 SQLite 事务；Flutter 只用 peek + ACK，绝不“读取后立即清空”。崩溃在保存和 ACK 之间时重读同一事件，由账本事件 ID 去重；被忽略和已入账记录仍保留事件身份防止重放。

原生队列设置容量上限，达到上限时保留既有待处理数据并计数告警；不静默覆盖。无关通知不落盘，不打印正文日志。用户可在页面清除待处理通知数据，告知会删除尚未入账的候选。系统备份排除原生队列。不会自动上传通知或截图。

## 界面

1. 顾问聊天：图片附件预览／移除，待确认操作入口，发送中取消与错误重试。
2. 待确认操作：清楚展示新增／修改字段、账户名称、金额与余额影响；确认、拒绝、已执行历史及撤销。
3. 支付通知页面：权限说明、启用开关、系统授权入口、状态信息、手动刷新与候选列表。
4. 候选核对：原文、识别依据和不确定项可见；编辑金额、日期、收支类型、分类和实际扣款账户，再保存。转账必须指定不同的转出／转入账户。退款不默认收入。

## 实施顺序

1. 保存规划，建立现有工程 Git 基线并创建 `feat/agent-notification`。
2. 提案与通知候选领域服务，补充原子性、幂等和冲突测试。
3. 智能体分页、设置工具、变更提案、多模态传输及 UI。
4. Kotlin 通知规则、SQLite 队列、系统权限和桥接，Flutter 待确认界面。
5. 运行 Dart 分析和测试、Android 原生测试及 release APK 构建，记录真实结果。

## 验证清单

自动测试：分页汇总与账户筛选；截图数据不进备份；图片能力拒绝及重试；模型不能直接执行写入；重复确认、失效提案、保存失败、撤销冲突；普通聊天与营销不误记；通知精确重复与疑似重复；ACK 前保存失败；未知账户和退款不能误入账。

小米 17 Pro 真机：记录系统／支付 App 版本；扫码、被扫、转账、退款通知；熄屏、退出、划掉任务、重启、撤权、强行停止后的恢复；同一通知更新与重复回调；断网采集；关闭／开启采集的待机 CPU、联网、唤醒和耗电对比。未连接真机与真实模型时必须明确标为未验证，不能用模拟测试替代覆盖率或耗电结论。
