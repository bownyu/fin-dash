# FinDash 0.5.5

日期：2026 年 10 月 4 日。Android 构建号：14。从 0.5.4 可直接覆盖升级。

## 轻量后台通知监听

- Android 通知监听、收件箱和开机 / 升级接收器运行在 `:payment_capture` 原生进程。该进程不创建 Flutter 引擎，不加载语音模型，不发起网络请求。
- 主界面通过不对外导出的 ContentProvider 按需通信，接口校验调用方 UID。仅原生进程读写原有 `payment_capture` 设置和 `payment_inbox.db`，避免跨进程 SharedPreferences 缓存失步。
- 连接中断后最多尝试三次重绑，间隔为 0、10、30 秒；连接成功、关闭采集或失去授权后停止重试。正常连接时无重试任务。开机、升级和进入 App 时按需恢复，不添加闹钟、后台轮询、唤醒锁或额外无障碍服务。
- 回调先按包名、通知标题和分组过滤，再交给一个后台线程解析；内存队列最多 64 项，线程空闲 10 秒后释放。SQLite 收件箱仍最多保存 1000 条，队列满时显示丢失计数。
- 原生分页最多 100 条且限制为约 128 KiB 原文体积，给 Binder 通信留出空间。账本持久化成功后才 ACK，崩溃重放与去重规则保持。
- “支付通知识别”增加电池优化状态及系统设置入口，可按手机系统允许自启动、后台运行和关联启动。

独立进程可以减少主界面对监听的影响，但不能绕过厂商清理策略或系统强行停止。断开期间的通知不能保证补回；真机待机功耗与特定手机清理后的恢复仍需要实测。

## 数据兼容

沿用原有设置、收件箱和账本，不修改 SQLite `user_version` 或备份 schema。保存开关后才更新运行状态；账本写入失败时保留通知供重试。

## 验证

- 静态检查通过；Flutter 全量测试 325 项通过，1 项因缺少本地私人样本跳过；Android 原生单元测试 26 项通过。
- 通知回归覆盖账本保存失败不 ACK、保存后崩溃重放、通知去重、批量确认原子性、退款关联和锁定校验。新增分页测试验证超过十页的通知同步 / 清除不会遗漏 ID，清除后的重放也不会重新进入待确认。
- Android 16（API 36）x86_64 临时模拟器使用独立测试包 `com.findash.fin_dash.validation`。原生测试读取旧版采集设置与 300 条每条含 4096 字原文的合成通知，跨进程分批读取、更新开关及 ACK，全程无丢失或重复；其他 UID 无法访问私有接口。
- 启用真实系统通知监听绑定后，启动主界面，再结束主进程。监听进程 PID 保持不变、连接仍有效；向已绑定服务传入合成微信支付回调，成功保存并读取金额 150 分的待确认记录。该验证使用合成回调，没有连接真实微信或支付宝账号。
- 采集后的空闲检查确认进程没有加载 Flutter / Sherpa 语音库，工作线程在 10 秒空闲超时后退出。该次模拟器 debug 测量的监听进程 PSS 为 44,694 KiB（约 43.6 MiB），包含 Android 运行时开销，不代表真机 release 的内存或功耗。
- 测试脚本为 [`scripts/test-payment-background.ps1`](../../scripts/test-payment-background.ps1)，仅接受模拟器并使用独立测试包。设备测试组件仅存在于 debug / androidTest 源码；release Manifest 已检查，不包含这些组件或测试包标识。没有新增运行或测试库依赖。
- ARM64 Flutter release 构建成功，应用 ID 为 `com.findash.fin_dash`，版本为 `0.5.5+14`；APK 签名验证通过，签名证书与 0.5.4 一致，可覆盖升级。插件仍使用项目内 `.pub-cache`。

真实微信 / 支付宝通知、厂商一键清理、重启 / 升级后的完整设备流程，以及待机功耗尚需在目标手机验证。模拟器中的“结束主进程”不等同于厂商按整个应用清理后台或系统“强行停止”。Android 的停止状态说明见[官方文档](https://developer.android.com/about/versions/15/behavior-changes-all#stopped-state)。

## 使用

在“支付通知识别”中开启“采集支付通知”，授予系统通知使用权。根据手机系统，通过同页的“电池优化设置”和“应用后台设置”允许后台运行、自启动或关联启动；这些入口只在点击时打开，不自动更改系统设置。
